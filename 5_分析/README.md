# 5_分析

## 役割
投稿した「自分の動画」のパフォーマンスを分析し、次のリサーチ・台本にフィードバックする工程。
※ここで扱う指標（特に平均再生率）は投稿者本人のアナリティクスでしか見られない非公開データのため、この工程は自分の投稿動画が対象。

## 最重要指標: 平均再生率
- ショートは急にアルゴリズムに乗る性質があるため、最重視すべきは**平均再生率（視聴維持率）**。
- 目安:
  - **40〜50秒の動画** → **70〜80%以上**が理想
  - **20秒の動画** → **80%以上**は欲しい
- 再生率が基準に届かない動画は、フック（冒頭）・尺・テンポを見直す。

## 重要指標: 登録者の伸び
- **再生数に対してチャンネル登録者数が増えているか**を確認する。
- 再生は伸びているのに登録が増えない場合、内容とチャンネルの方向性（退職給付金）のズレや、CTA（プロフ/LINE誘導）の弱さを疑う。

## その他の指標
- いいね・保存・シェア・コメント数
- プロフィール遷移数、LINE登録などのコンバージョン（成果）

## やること
- 各動画の指標収集（平均再生率・再生数・登録者増・いいね・保存・シェア・プロフ遷移・LINE登録）
- 伸びた動画/伸びなかった動画の要因分析（フック・尺・テーマ別）
- 分析結果を 1_リサーチ へフィードバック（次のネタ・参考動画選定に活かす）

## 入力（前工程から受け取るもの）
- 4_投稿 の 投稿ログ（投稿ID・URL）
- TikTokアナリティクスの数値（平均再生率など）

## 出力（フィードバック先）
- 分析レポート（勝ちパターン/負けパターンのまとめ）
- 次に試すべきネタ・改善案 → 1_リサーチ へ

## 出力先の例
- `分析レポート_YYYYMM.md` / `metrics.csv` など

---

## 使い方（実装済み・手動入力＋CSV）
数値の取得は当面**手動**（TikTokアプリ/管理画面のインサイトを見て入力）。育ったらブラウザ自動化に差し替える。
スクリプトは標準ライブラリのみで動くので venv 不要（`python3` 一発）。尺はffprobeで自動取得。

### ① 指標を記録する（投稿ごと・確認時間は毎回そろえる／例: 投稿24h後）

**(a) 自動取得（推奨・一部項目）** — `metrics_fetch.py`
TikTok Studioのコンテンツ一覧をブラウザ自動化で読み、post_logのキャプションで動画を突合して
**再生数・いいね・コメント・尺・投稿日**を自動でCSV追記する。4_投稿 の browser_ctx（CDP接続で
検知回避）とログインセッション(.chrome-profile)を共有するので、playwright入りの4_投稿 venvで実行:
```bash
cd 5_分析/scripts
../../4_投稿/scripts/.venv/bin/python metrics_fetch.py --video 本番_015_TikTok
../../4_投稿/scripts/.venv/bin/python metrics_fetch.py --inspect   # DOM確認(selector調整用)
```
※前提: 4_投稿/scripts/login.py 済み。**平均視聴秒・継続率・おすすめ%・視聴者属性は自動未取得**
（TikTok Studioの動画別詳細がURL直叩き不可のため。次段で対応予定）。

**(b) 手動入力／深い指標の追記** — `record.py`
```bash
# 対話モード（数値を順に聞かれる。分かる項目だけでOK）
python3 record.py 本番_015_TikTok
# またはフラグでまとめて
python3 record.py 本番_015_TikTok --views 3200 --avg-watch 9.5 \
    --full-view 42 --hold1s 55 --fyp 96 --likes 120 --saves 15 --line 5
```
→ `5_分析/metrics.csv` に1行追記。**視聴維持率(%)＝平均視聴秒÷尺秒**は自動計算。
投稿日時は `4_投稿/ログ/post_log.csv` から自動で拾う。尺はffprobeで自動取得。

### ①.5 角度×実績を書き出す（台本の重複判定が読む）【2026-09-04 追加】
```bash
cd 5_分析/scripts
../../4_投稿/scripts/.venv/bin/python update_results.py            # 直近30本を取り直す
../../4_投稿/scripts/.venv/bin/python update_results.py --limit 60
```
→ `5_分析/実績.tsv`（動画名・公開日・再生数・角度・タイトル）。
**`2_台本生成/scripts/write_script.py` の重複判定がこれを読む。**
1万再生以上＝【勝ち筋】（重複を理由に落とさない・むしろ再訪する）、
1万未満＝【沈んだ角度】（同じ切り口なら不採用）、公開7日未満＝【判定中】。

以前は「採用履歴.tsv のメモ欄」を渡していたが、自動運用では採用行のメモが空で、
埋まるのは `pipeline.mark_rejected` が書く【不採用】理由だけ。つまり
**一度も作っていない角度を「既に扱った角度」としてLLMに渡していた**。
その結果、当たり筋（国保・住民税の減免＝032で243,000再生）が
8/17〜9/3で9本連続の不採用になっていた。**週1回は更新すること**（1本20〜40秒・
ログイン済Chromeを使うので `login.py` 済みが前提）。

### ② 分析レポートを出す
```bash
python3 analyze.py            # ターミナルに表示
python3 analyze.py --month 2026-07   # 月で絞る
python3 analyze.py --md       # レポート/分析レポート_YYYYMM.md にも保存
```
→ 動画別サマリー＋各動画の指摘＋勝ち/要改善を出力。判定は下記しきい値。

### 判定のしきい値（analyze.py 冒頭で調整可）
| 指標 | 目標 | 意味 |
|---|---|---|
| 視聴維持率 | 理想=尺依存（20s帯80%/40〜50s帯75%/長尺60%）、現実の下限15% | 最重要。届かなければ尺・テンポ・フック見直し |
| 継続率1秒 | 40%以上 | 冒頭1秒=サムネ相当。低ければ冒頭改善 |
| おすすめ流入率 | 95%以上 | 低いと投稿時間変更/シャドウバン確認 |

いいね・保存・シェア・コメント・プロフ遷移・LINE登録はサブ評価として記録。

### 手入力する数値の在りか（TikTokインサイト）
- 動画をタップ→右下「他のインサイト」: 再生数・平均視聴秒・フル視聴率
- パフォーマンス→エンゲージメント: 継続率（1秒時点）、トラフィックソース（おすすめ%）
- **視聴者タブ**（動画の解説で「非常に重要」）: 性別・年齢・位置
  - `--audience "40代男性/東京"` のように主要層を記録
  - `--target-match ○/△/✗` で自チャンネルのターゲット（退職検討層）と一致したかを記録
  - 対話モードでは視聴者タブの項目として最後にまとめて聞かれる

### アカウントのインサイト（毎日は不要）
プロフ右上「三」→クリエイターツール→インサイト。フォロワー100人超で推移・男女比が見れる。
**動画が伸びなくなった時**に、フォロワー属性（男女比・年代）がターゲットとズレていないか確認する用途。

### フィードバック（→ 1_リサーチ）
「勝ち」判定の動画の型・フック・テーマ、および**ターゲットに届いた（一致○）動画**を軸に横展開する。
analyze.py の「視聴者属性（ターゲット到達）」セクションが、○の動画と✗の動画を仕分けして出す。

### ★ 週次レビュー（毎週日曜22:00・全自動）【2026-09-07 追加】
①〜③を1コマンドで通し、**結果を次の生成に自動で反映する**。Discord Bot が毎週日曜22:00に呼ぶ
（`分析` と送れば手動でも回る）。
```bash
cd 5_分析/scripts
python3 weekly_review.py              # 通し（実測の取り直しでChromeを使う。10〜20分）
python3 weekly_review.py --no-fetch   # 実測の取り直しを飛ばす（Chrome不要・数十秒）
python3 weekly_review.py --dry-run    # 何が変わるかだけ見る（書き換えない）
```
| 工程 | やること |
|---|---|
| ① | `update_results.py` で `実績.tsv` を最新に（失敗しても前回の実績で続行） |
| ② | `feedback_context.py` の材料束 ＋ 実績（角度×再生数） |
| ③ | LLMを**1回だけ**呼ぶ（`プロンプト_週次反映.md`） |
| ④ | **反映**: `1_リサーチ/検索語.json` と `2_台本生成/重点方針.md` を書き換える |
| ⑤ | **下書き**: `1_リサーチ/ネタ提案_YYYYMMDD.md`（採用/却下は社長） |

- **機械が書き換えるのは④の2ファイルだけ**。`台本作成ルール.md` や各スクリプトのコードには触らない。
  人が書いたものと機械が書くものを別ファイルに分けてあるので、どちらを直しても喧嘩しない。
- 検索語は**1語でも形が変なら丸ごと据え置く**。ここが壊れると翌朝から1本も作れなくなるため。
- 上書き前の値は `レポート/週次_YYYYMMDD.md` に丸ごと残る（戻す時はここから／git でも戻せる）。
- 反映されるのは方針まで。**投稿には一切触らない**ので、走っても勝手に何かが世に出ることはない。

### ③ フィードバック提案を作る（AI下書き → 社長承認）
分析結果＋参考文献をまとめてAIに「次に作るべきネタ」を提案させる工程。2_台本生成 と同じく
**決まった収集＝スクリプト／判断＝AI／採用＝人間** の分担。
```bash
cd 5_分析/scripts
python3 feedback_context.py            # 材料束を表示（analyze結果＋投稿訴求＋採用履歴＋過去台本＋参考プール）
python3 feedback_context.py --md       # 5_分析/レポート/フィードバック素材_YYYYMMDD.md に保存
```
- **データ充足度で強さを自動調整**: 材料束の先頭が実測本数を見て 🅐一般論／🅑僅少／🅒初期／🅓データ駆動 を判定。
  実測が薄いうちは「仮説」までしか出させない（過剰な結論を防ぐ）。
- このあとAIが `../プロンプト_フィードバック.md` に従って `1_リサーチ/ネタ提案_YYYYMMDD.md` に**下書き**を書く。
  各案に `[ ] 採用 / [ ] 却下` が付き、**社長が選んだ案だけ** use_ref.py 等で次工程へ流す（人間承認ゲート）。
- 景表法（額面の断定訴求NG）・参考動画の30日再利用ロックはプロンプト側で明示的に守らせる。
